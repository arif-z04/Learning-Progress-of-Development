# Linux Fundamentals: Processes, Signals, Services & Logs

## 1. Processes

### 1.1 Definition

A **process** is a running instance of a program managed by the operating system. It has its own virtual address space, a process ID, and operating-system-managed resources.

Examples:
- A running web browser
- An ASP.NET Core application
- A MySQL database server
- A Python script

### 1.2 Important Process Concepts

| Concept | Meaning |
|---|---|
| PID | Process ID; identifies a process |
| PPID | Parent Process ID |
| Foreground process | Runs interactively in the terminal |
| Background process | Runs without occupying the terminal's foreground |
| Daemon | A process that runs in the background to provide a service |
| Exit code | A numeric status indicating how a process terminated |

An exit code of `0` conventionally means success. A nonzero exit code generally indicates an error or another unsuccessful outcome.

### 1.3 Inspect Processes

```bash
ps aux
```

Lists processes with details such as CPU and memory usage.

```bash
ps -ef
```

Displays processes in a different format, including parent process information.

```bash
pgrep -a dotnet
```

Finds processes whose names match `dotnet` and displays their command lines.

```bash
ps -p PID -o pid,ppid,stat,%cpu,%mem,comm
```

Replace `PID` with a real process ID to inspect that process.

```bash
top
```

Displays running processes and updates resource statistics interactively.

### 1.4 Start a Process

Run a Python program in the foreground:

```bash
python3 main.py
```

The terminal remains occupied until the process exits or is suspended.

Run a program in the background:

```bash
python3 main.py &
```

The `&` runs the command asynchronously in the shell. It does not automatically make the program a persistent system service.

### 1.5 Shell Job Management

```bash
sleep 300 &
```

Starts a background job.

```bash
jobs
```

Lists jobs managed by the current shell.

```bash
fg
```

Brings the current or most recently selected job into the foreground.

```bash
bg
```

Resumes a suspended job in the background.

Press `Ctrl+C` to interrupt a foreground process, or `Ctrl+Z` to suspend it in an interactive terminal.

**Important:** Shell jobs and operating-system processes are related but different concepts. A background process can continue running even when it is not the shell's foreground job, although its behavior after terminal closure depends on how it was started.

## 2. Signals

### 2.1 Definition

A **signal** is a notification sent to a process to inform it that an event occurred or that it should perform a particular action.

Signals are commonly used to interrupt, terminate, or control processes in Linux.

### 2.2 Common Signals

| Signal | Number on Linux | Purpose |
|---|---:|---|
| `SIGHUP` | 1 | Traditionally indicates a hangup; some services use it to reload configuration |
| `SIGINT` | 2 | Interrupt; commonly generated by `Ctrl+C` |
| `SIGKILL` | 9 | Forces termination; cannot be caught or ignored |
| `SIGTERM` | 15 | Requests termination; a process can handle or ignore it |
| `SIGSTOP` | 19 on common Linux architectures | Stops a process; cannot be caught or ignored |
| `SIGCONT` | 18 on common Linux architectures | Continues a stopped process |

Signal numbers can vary across operating-system platforms. Using signal names is generally more portable.

### 2.3 Send a Signal Using `kill`

Despite its name, `kill` can send different signals, not only terminate processes.

Request graceful termination:

```bash
kill PID
```

This normally sends `SIGTERM`.

Send an explicit termination request:

```bash
kill -TERM PID
```

Force termination:

```bash
kill -KILL PID
```

Stop and resume a process:

```bash
kill -STOP PID
kill -CONT PID
```

Replace `PID` with the actual process ID.

### 2.4 SIGTERM vs. SIGKILL

**SIGTERM**
- Requests that a process terminate.
- Can be handled by the application.
- Allows an application to clean up resources and save state where possible.
- Is usually the first choice when stopping an ordinary process.

**SIGKILL**
- Forces the kernel to terminate the process.
- Cannot be caught, blocked, or ignored by the process.
- Does not allow application-level cleanup handlers to run.
- Should generally be used only when graceful termination fails.

**Best practice:** Try graceful termination first. Force-killing a database or another stateful application may interrupt operations and require recovery.

### 2.5 Practical Example

Start a test process:

```bash
sleep 300 &
```

Find its PID:

```bash
pgrep -a sleep
```

Send a termination request:

```bash
kill -TERM PID
```

Replace `PID` with the number returned by `pgrep`.

Verify that the process has exited:

```bash
pgrep -a sleep
```

If there are other `sleep` processes, inspect the output carefully to distinguish them.

**Safety note:** Always verify the target PID before sending signals. Avoid running destructive commands against processes you do not understand.

## 3. Services and systemd

### 3.1 Definition

A **service** is a program or application that provides functionality to other programs or users, often in the background.

Examples:
- Database servers
- Web servers
- SSH servers
- Network management services

A service may be implemented as one or more processes.

### 3.2 What Is systemd?

`systemd` is a system and service manager used by many modern Linux distributions, including common Arch Linux installations.

It can:
- Start services during boot
- Stop and restart services
- Manage service dependencies
- Track service states
- Collect logs through the journal
- Restart services according to configured policies

A **systemd unit** represents a managed resource. A `.service` unit describes a service.

### 3.3 Check Whether systemd Is Running

```bash
systemctl is-system-running
```

This reports the overall system state. Depending on the system, it may return states such as `running`, `degraded`, or `starting`.

### 3.4 Inspect a Service

Check the status of the SSH service:

```bash
systemctl status sshd
```

On many Arch-based systems, the OpenSSH server service is named `sshd`. Other distributions may use different names.

Check another service:

```bash
systemctl status NetworkManager
```

The exact service name depends on which networking software is installed.

### 3.5 Common systemctl Commands

| Command | Purpose |
|---|---|
| `systemctl status NAME` | View service status and recent logs |
| `systemctl start NAME` | Start a service now |
| `systemctl stop NAME` | Stop a running service |
| `systemctl restart NAME` | Restart a service |
| `systemctl reload NAME` | Ask a service to reload configuration, if supported |
| `systemctl enable NAME` | Configure a service to start at boot |
| `systemctl disable NAME` | Disable its boot-time activation |
| `systemctl is-active NAME` | Check whether a service is active |
| `systemctl is-enabled NAME` | Check whether it is enabled at boot |
| `systemctl list-units --type=service` | List loaded service units |

Replace `NAME` with the actual service name.

Some operations require elevated privileges, for example:

```bash
sudo systemctl restart sshd
```

**Important distinctions:**
- `start` runs the service now.
- `enable` configures it to start automatically at boot.
- `restart` stops and starts it again.
- `reload` asks the service to reload configuration without a full restart, if supported.

A service can be enabled but not currently running. It can also be running without being enabled at boot.

### 3.6 Services vs. Processes

| Process | Service |
|---|---|
| A running instance of a program | A managed application or background function |
| Identified by a PID | Often managed through a service manager |
| Can be started directly from a terminal | Can be configured to start at boot |
| Can exit independently | May have restart policies and lifecycle management |

A service generally runs as a process, but not every process is a system service.

## 4. Logs

### 4.1 Definition

A **log** is a record of events generated by an operating system, application, or service.

Logs help developers and system administrators understand what happened before, during, and after a failure.

### 4.2 Common Types of Logs

- **Application logs:** Application activity, errors, warnings, and debugging information.
- **System logs:** Operating-system events.
- **Service logs:** Events produced by a service such as a database or web server.
- **Security logs:** Authentication and security-related events.
- **Access logs:** Records of requests received by a web server.

### 4.3 Common Log Levels

| Level | Purpose |
|---|---|
| Trace | Very detailed diagnostic events |
| Debug | Information useful during development and debugging |
| Information | Normal application events |
| Warning | An unexpected condition that may not be a failure |
| Error | An operation failed |
| Critical | A severe failure requiring urgent attention |

Not every application supports all these levels or uses exactly the same names.

### 4.4 Where Are Linux Logs Stored?

Many Linux systems store persistent or temporary log files under:

```text
/var/log/
```

Examples may include:
- System journal-related files
- Authentication logs
- Web server access and error logs
- Database logs

The exact files depend on the distribution and logging configuration.

On systems using systemd, many system and service logs are collected by `journald` and can be inspected with `journalctl`.

### 4.5 Read Logs Using journalctl

Show recent journal entries:

```bash
journalctl -n 50
```

Show logs for a particular service:

```bash
journalctl -u sshd
```

Show the latest service logs:

```bash
journalctl -u sshd -n 50
```

Follow new log entries in real time:

```bash
journalctl -u sshd -f
```

Show logs from the current boot:

```bash
journalctl -b
```

Show errors from the current boot:

```bash
journalctl -b -p err
```

Press `Ctrl+C` to stop following a live log stream.

**Note:** Access to some logs may require elevated privileges or membership in an authorized system group.

### 4.6 Read Traditional Log Files

If the application writes to a regular log file, use commands such as:

```bash
tail -n 50 application.log
```

Displays the last 50 lines.

```bash
tail -f application.log
```

Follows new lines as they are written.

```bash
less application.log
```

Opens a file for interactive reading and searching.

### 4.7 Log Rotation

Applications can generate large amounts of log data. **Log rotation** manages log growth by archiving, compressing, or removing older logs according to configured retention rules.

Without suitable retention policies, logs can consume substantial storage space.

## 5. Troubleshooting a Failed Application

Suppose an ASP.NET Core application is not responding.

A practical investigation sequence is:

### Step 1: Check Whether the Process Exists

```bash
pgrep -a dotnet
```

If no matching process appears, the application may not be running, or its command line may not match the search.

### Step 2: Check Its Service Status

If the application is managed by systemd:

```bash
systemctl status myapp.service
```

Replace `myapp.service` with the real unit name.

### Step 3: Inspect Its Logs

```bash
journalctl -u myapp.service -n 100
```

Look for startup errors, database connection failures, configuration errors, and exceptions.

### Step 4: Follow Logs While Reproducing the Problem

```bash
journalctl -u myapp.service -f
```

Reproduce the issue and observe new log entries.

### Step 5: Check Resource Usage

```bash
top
free -h
df -h
```

Check whether CPU is saturated, memory is under pressure, or a filesystem is full.

### Step 6: Restart Only When Appropriate

If the evidence suggests a restart is appropriate:

```bash
sudo systemctl restart myapp.service
```

Then inspect the status and logs again. Restarting may temporarily hide the symptom without fixing its underlying cause, so preserve useful error evidence first.

Use a harmless test process to practice process management.

### Task 1: Start a Background Process

```bash
sleep 300 &
```

### Task 2: Find It

```bash
pgrep -a sleep
jobs
```

Notice that `jobs` lists shell-managed jobs, while `pgrep` searches processes.

### Task 3: Stop It Gracefully

```bash
kill -TERM PID
```

Replace `PID` with the actual process ID.

### Task 4: Inspect a Real Service

```bash
systemctl status sshd
```

If `sshd` is not installed, inspect a service that exists on your system instead.

```bash

```

```bash
top
free -h
df -h
```

Observe how processes consume CPU and memory and how much filesystem space remains.

## 7. Quick Revision

| Concept | Key Idea | Useful Commands |
|---|---|---|
| Process | Running instance of a program | `ps`, `pgrep`, `top` |
| PID | Identifier of a process | `ps -p PID` |
| Signal | Notification sent to a process | `kill`, `pkill` |
| SIGTERM | Requests graceful termination | `kill -TERM PID` |
| SIGKILL | Forces process termination | `kill -KILL PID` |
| Service | Managed application or background function | `systemctl` |
| systemd | System and service manager | `systemctl status` |
| Log | Record of system or application events | `journalctl`, `tail` |
| Log following | Observe newly written entries | `journalctl -f`, `tail -f` |
| Resource monitoring | Inspect CPU, RAM, and storage usage | `top`, `free -h`, `df -h` |

### Key Points to Remember

1. A process is a running program.
2. A signal communicates an event or action request to a process.
3. `SIGTERM` requests termination; `SIGKILL` forces it.
4. A service is commonly managed by a service manager such as systemd.
5. `start` and `enable` have different meanings.
6. Logs provide evidence for diagnosing failures.
7. `journalctl` is useful for inspecting systemd journal entries.
8. Check process state, service status, logs, and resources before assuming a restart will fix a problem.
9. Prefer graceful shutdown and verify process identities before sending signals.

### Learning Milestone

You should now be able to inspect running processes, manage harmless test processes, explain common Linux signals, check systemd service status, read service logs, and follow a basic troubleshooting workflow for a web application.
